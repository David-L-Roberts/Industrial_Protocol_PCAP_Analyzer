# 02: Modbus TCP Trace Spans, Timeline Events & Cross-Table Correlation

**What to build:** Instrument the pure Modbus TCP decoder to emit complete **Trace Spans** with low-cardinality operation names, rich protocol attributes, and timeline events for every Modbus TCP exchange—and stamp the exact shared **Trace ID** and **Span ID** onto all correlated **RED Metrics**, **Captured Command Events**, and **Extracted Data Points**.

When tracing is enabled (`TestSession.StoreTraceSpans == true`), every Modbus read (`FC 01–04`), write (`FC 05, 06, 15, 16`), exception (`FC >= 0x80`), timeout (`Timeout`/`TimeoutAtEof`), malformed frame, and unpaired orphan response produces a structured `TraceSpanRecord` ready for Grafana Trace View and Node Graph. Request-side writes pre-allocate `(TraceId, SpanId)` at request registration so request-side command events and data points correlate 1:1 with the later response or timeout span in a single streaming pass. When tracing is disabled (`StoreTraceSpans == false`), zero spans are emitted and all `trace_id`/`span_id` fields remain `null`.

**Blocked by:** 01: End-to-End Trace Span Persistence Spine, Configuration & Opt-Out

**Status:** ready-for-agent

- [ ] Modbus read requests (`FC 01–04`) pre-allocate deterministic `(TraceId, SpanId)` values and attach `PendingSpanContext` (resolved `ClientEndpoint`, `ServerEndpoint`, `ServiceName = ServerEndpoint`, low-cardinality `OperationName` such as `Modbus FC03 ReadHoldingRegisters`, request IPs/ports, `modbus.unit_id`, `modbus.register_type`, `modbus.start_address`, `modbus.quantity`, request byte length, and `RequestSent` event) when registering with `VirtualClockRedEngine`.
- [ ] Modbus write requests (`FC 05, 06, 15, 16`) pre-allocate `(TraceId, SpanId)`, attach `PendingSpanContext` including a `CommandIssued` event, and immediately stamp the same `(TraceId, SpanId)` onto emitted `CapturedCommandEventRecord` and request-side `ExtractedDataPointRecord` rows.
- [ ] Matched Modbus responses emit a `RequestResponse` `TraceSpanRecord` spanning `[requestTimestamp, responseTimestamp]` with `DurationMs`, `StatusCode = Ok` (or `Error` with `StatusMessage` and `modbus.exception_code` + `ProtocolException` event for `FC >= 0x80` exceptions while keeping base low-cardinality `OperationName`), response byte length, `tags.matched_count`, `tags.changed_count`, `ResponseReceived` event, and up to 10 `TagValueChanged` events (setting `tags.changes_truncated = true` when exceeded), while stamping `(TraceId, SpanId)` onto all response-side `ExtractedDataPointRecord` and `ProtocolTransactionRecord` rows.
- [ ] Timed-out Modbus requests (both `Timeout` and `TimeoutAtEof`) flush via `VirtualClockRedEngine` with the exact pre-allocated `(TraceId, SpanId)` shared with any request-side write commands/data points and emit `Error` spans carrying a `TimeoutExpired` event.
- [ ] Unpaired Modbus server responses (`TryCompleteResponse == false`) emit zero-duration `OrphanResponse` spans (`protocol.unpaired = true`, `ServiceName = ClientEndpoint`, `StatusCode = Error` if exception else `Unset` with `StatusMessage = "ORPHAN_RESPONSE"`) without emitting a `ProtocolTransactionRecord`.
- [ ] Malformed Modbus frames in either direction stamp `(TraceId, SpanId)` onto the malformed `ProtocolTransactionRecord` and emit a zero-duration `Malformed` error `TraceSpanRecord` (`OperationName = "Modbus MalformedFrame"`).
- [ ] When `StoreTraceSpans` is `false`, no `TraceSpanRecord` rows are emitted and `TraceId`/`SpanId` remain `null` on all `ProtocolTransactionRecord`, `ExtractedDataPointRecord`, and `CapturedCommandEventRecord` outputs.
- [ ] Unit tests cover every Modbus span path (reads, writes, exceptions, mid-stream/EOF timeouts, malformed, orphan responses, tag-change event capping at 10, and opt-out mode) using synthetic frames only; live Modbus PCAP integration tests confirm `trace_spans` persistence and 100% foreign correlation across `red_transactions`, `captured_command_events`, and `tag_values`.
